# Minor Safety

Required by section 25. Describes how ThinkFirst behaves when a student says something that
is not about schoolwork, and why each decision was made that way.

- **Last updated:** 2026-08-07, session
  [12](logs/2026-08-07-12-phase-8-safety-and-security.md).
- **Implementation:** `lib/safety/response.ts`, `lib/safety/resources.ts`,
  `lib/safety/safety-event.ts`, rule R8 in `services/ai-gateway/src/policy/index.ts`, and the
  safety branch of `app/api/session/chat/route.ts`.

---

## The one decision that shapes everything else

**A safety response is composed in code, not generated by a model.**

Until session 12 the policy engine correctly returned `safety_redirect`, and the tutoring
route then called the tutor model anyway with `Action: safety_redirect` in its system prompt.
Section 41.1 names that shape exactly: "a prompt instruction to obey the plan is not
enforcement." A student disclosing self-harm received generated text, with no support
resources attached, and no guarantee the model treated the turn as a safety turn at all.

Now a safety turn short-circuits before any tutor call. The message comes from constants. The
one turn that must not be improvised is the one where a child says something is wrong.

Consequences, all deliberate:

- The response is deterministic and reviewable by reading the source.
- It cannot be steered by prompt injection, because no prompt is involved.
- It cannot fail on a quota error, a timeout or a malformed model response.
- It is not translated by a model; each locale's text is written out and reviewable.

## Categories and dispositions

Section 24 requires four things to be "clearly distinguished". They are a closed union in
`lib/safety/response.ts`, so a new category cannot be handled by an ad-hoc string:

| Response class | Meaning |
|---|---|
| `emergency_guidance` | Possible immediate risk to the student. Support guidance is attached |
| `teacher_review` | A human at the school should look. Guidance attached where useful |
| `educational_redirect` | Off-limits for schoolwork, no welfare concern |
| `abuse_report` | Platform misuse, for administrators rather than teachers |

| Classifier category | Response class | Teacher flagged | Resources shown |
|---|---|---:|---:|
| `self_harm` | `emergency_guidance` | yes | yes |
| `abuse` | `emergency_guidance` | yes | yes |
| `bullying` | `teacher_review` | yes | yes |
| `violence` | `teacher_review` | yes | no |
| `sexual_content` | `educational_redirect` | no | no |
| `illegal_activity` | `educational_redirect` | no | no |
| `personal_data` | `educational_redirect` | no | no |
| `other` | `educational_redirect` | no | no |

**Why the last four are not flagged.** A student asking a curious or off-colour question is
not a welfare concern, and flagging it would teach students that the tool reports them. A
tool that feels like surveillance is one they will not use when something is actually wrong,
which costs more than the flag gains. The line drawn here is welfare risk, not
inappropriateness.

## Section 24 requirements, line by line

Each is a property of the constants in `lib/safety/response.ts` and checkable by reading them.
Where a test asserts it, the test is named.

| Requirement | How it is met |
|---|---|
| Respond calmly | Messages open by acknowledging, not alarming: "Thank you for telling me" |
| Avoid graphic detail | No message names or describes any method or act |
| Encourage contacting a trusted adult | Every `emergency_guidance` and `teacher_review` message does, and the guidance list leads with it |
| Use configured local support resources | `getSafetyResources` supplies them when configured |
| **Never invent emergency phone numbers** | No number is configured anywhere. Asserted by "invents no emergency number" |
| Avoid promising secrecy | The message states the opposite: "I can't keep it private if you might be in danger." Asserted by a test |
| Avoid acting as a therapist | Messages redirect to a human and offer no counsel |
| Avoid interrogating the student | No safety message contains a question mark at all. Asserted by a test across every category |
| Escalate per deployment policy | `safetyEvents` records the disposition; `auditLogs` records the raised flag. No automatic external notification, which is a deployment decision |
| Do not expose classifications to classmates | `safetyEvents` has no client read at all. Four rules negatives |

## Why no hotline numbers ship

Section 24 says "Never invent emergency phone numbers" and "Do not ship unverified
placeholder hotline information in production." The Phase 8 exit criterion repeats it.

Nothing in this environment can verify a crisis line for any jurisdiction. So the resource
tables ship **empty**, and the code refuses to serve an unverified entry even if one is added
later: `isServableContact` requires `verified: true`, a recorded reviewer, a recorded date,
and a contact string that does not match the placeholder patterns in `looksLikePlaceholder`.

This is the inverse of the usual instinct, and it is the right way round. A wrong crisis
number is worse than no number: it consumes the one moment a student reached out. A missing
number is visible and fixable; a wrong one looks like help.

What ships instead is guidance that is true and safe without any external contact: tell a
parent or guardian, tell a teacher or school counsellor, contact local emergency services if
someone is in immediate danger. When no contacts are configured, the absence is stated —
"this installation has not had local support services configured yet" — so it reads as an
unfinished configuration rather than a rendering failure.

### Adding real resources

1. Edit `SAFETY_RESOURCES` in `lib/safety/resources.ts` for the locale.
2. Add each contact with `verified: true`, `verifiedBy` and `verifiedAt`.
3. Set `lastReviewedAt`.
4. Run `npx vitest run tests/policy/safety-resources.test.ts`. The suite fails if any
   configured entry is unservable, so a half-finished edit does not ship.
5. Re-review on a schedule. Numbers change; a verified-in-2026 entry is not verified in 2030.

## What a safety turn does not do

Three omissions, each a requirement rather than an oversight.

**It is not scored.** `recordLearningEvidence` is skipped entirely. A crisis disclosure is not
an attempt at a mathematics problem, and running the evidence pipeline would both fold it into
the Independence Score and send it to the evaluator model. §56.4 forbids scoring a student
down for a system failure; doing it for a disclosure of harm would be worse.

**It does not reset the hint ladder.** R8 sets `allowedHintLevel: 0`, but the session's stored
`currentHintLevel` is left untouched. Writing the zero back would silently undo the progress
of a student who had legitimately reached level 4 before the conversation turned, which is a
punishment for disclosing.

**It does not store what the student wrote, twice.** `safetyEvents` holds the category, the
disposition, the classifier confidence and a pointer to the turn. The words stay on the turn,
under the student's own ownership scope. Asserted by "stores no student message content".

## The student is told

The workspace renders a `emergency_guidance` or `teacher_review` turn in a distinct amber
panel with `role="alert"`, and when a flag was raised it says so: "A teacher at your school
has been told you may want to talk. Your classmates cannot see this."

Both halves are deliberate. Saying a teacher was told follows from the prohibition on
promising secrecy — silence about the flag would be an implied promise. Saying classmates
cannot see it is the reassurance a student actually needs, and it is true: `safetyEvents` has
no client read.

The styling is driven by `safetyMetadata.responseClass` on the server-written turn, never by
the message text, so no student can trigger the panel by typing something that looks like a
safety message.

## Known gaps

1. **No human review surface.** `safetyEvents` records `reviewStatus: 'awaiting_review'` and
   nothing in the application ever changes it. The flag is recorded and audited; no teacher
   page lists flags yet. This is the largest gap in this document, and it is stated plainly
   because a flag nobody reads is not an escalation. The collection deliberately has no client
   read, so the surface must be a server route.
2. **No verified contacts**, as above. Requires human verification per deployment.
3. **No external escalation.** No email, webhook or SMS on an emergency classification.
   Section 24 defers escalation to "deployment policy", and there is no deployment.
4. **Classification depends on one model call.** A classifier that misses a disclosure means
   the turn is treated as ordinary tutoring. Mitigated in one direction only: an unusable
   classifier response falls back to the most restrictive analysis, but a *confident wrong*
   answer is not caught. There is no second opinion and no keyword safety net.
5. **Two locales only**, `en` and `vi`, matching what the rest of the application supports.
